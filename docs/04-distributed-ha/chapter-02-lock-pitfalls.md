# 第2章 分布式锁的坑

> Redisson 帮我们封装了大部分细节，但分布式锁仍然有三个「深坑」需要理解：锁超时导致并发、误删别人的锁、主从切换丢锁。理解了这三个坑，你才知道 Redisson 的看门狗、token 校验、红锁到底在解决什么问题。

---

## 2.1 坑一：锁超时导致并发

**现象**：业务执行时间超过了锁的有效期，锁自动释放，另一个线程拿到锁，导致两个线程同时进入临界区。

```text
线程A 加锁(10s) → 业务执行了 15s
                    ↓ 10s 时锁自动释放
线程B 加锁成功 → 与 A 并发执行 → 数据错乱
```

**根因**：锁的 `leaseTime` 设得太短，或者业务存在不可控的耗时（GC 停顿、网络抖动、慢 SQL）。

**解法**：

1. **用看门狗**：不指定 `leaseTime`，让 Redisson 自动续期（见第 1 章）；
2. **评估业务耗时**：如果指定 `leaseTime`，必须确认它大于业务最长执行时间，并留足余量。

```java
// 错误：业务可能超过 10s，锁提前释放
lock.lock(10, TimeUnit.SECONDS);

// 正确：业务耗时不确定，交给看门狗续期
lock.lock();
```

> 判断标准：**你能确定业务最坏耗时吗？能，就指定 leaseTime；不能，就用看门狗**。

---

## 2.2 坑二：误删别人的锁

**现象**：线程 A 的锁过期释放后，线程 B 拿到了锁；此时线程 A 的业务才执行完，去释放锁，结果把 B 的锁删了。

```text
线程A 加锁(10s) → 业务执行 15s（锁已过期）
                 → 线程B 加锁成功
                 → 线程A 执行完 unlock() → 误删了 B 的锁
```

**根因**：释放锁时没有校验「这把锁是不是我加的」。

**解法**：释放锁时必须校验锁的持有者。手写锁用 token 校验 + Lua 原子删除，Redisson 已经内置了这个校验：

```java
// Redisson 的 unlock() 内部会校验：只有当前线程持有的锁才会被释放
if (lock.isHeldByCurrentThread()) {
    lock.unlock();
}
```

> `isHeldByCurrentThread()` 就是 Redisson 内置的「归属校验」。手写分布式锁时，这个校验必须用 Lua 保证原子性（判断和删除不能分开）。

## 2.3 坑三：主从切换丢锁

这是最隐蔽、也最致命的坑。**单节点 Redis 加锁，主节点宕机后，锁还没同步到从节点，从节点提升为主节点，锁就丢了**。

```text
主节点 有锁 lock:order
   ↓ 主节点宕机（锁尚未同步到从节点）
从节点 提升为主节点（没有这把锁）
   ↓
线程B 在新主节点加锁成功 → 与 A 并发执行
```

**根因**：Redis 主从复制是**异步**的，主节点上的写操作不会立即同步到从节点。主节点故障时，未同步的锁数据就永久丢失了。

**Redisson 的解法——红锁（RedLock）**：

红锁的思路是「多节点投票」：同时在 N 个独立的 Redis 节点上尝试加锁，只有当**超过半数（N/2+1）**节点加锁成功，才认为获取锁成功。

```java
RLock lock1 = redissonClient.getLock("lock:order:1");
RLock lock2 = redissonClient.getLock("lock:order:2");
RLock lock3 = redissonClient.getLock("lock:order:3");

RedissonRedLock redLock = new RedissonRedLock(lock1, lock2, lock3);
try {
    // 尝试在 3 个节点加锁，成功 2 个以上才算成功
    if (redLock.tryLock(3, 10, TimeUnit.SECONDS)) {
        // 业务
    }
} finally {
    redLock.unlock();
}
```

---

## 2.4 红锁的争议与取舍

红锁虽然解决了「主从切换丢锁」，但业界对其争议很大：

| 维度 | 说明 |
| :-- | :-- |
| 优点 | 多节点投票，单点故障不丢锁 |
| 缺点 | 性能差（N 次加锁）、复杂度高、成本高 |
| 争议 | 分布式系统大佬 Martin Kleppmann 认为红锁模型有缺陷 |

**务实建议**：

| 场景 | 推荐 |
| :-- | :-- |
| 一般业务（允许极小概率并发） | 单节点 Redisson 锁 + 看门狗，够用 |
| 强一致、不允许并发 | 考虑 ZooKeeper / etcd 这类强一致存储做锁 |
| 折中 | 红锁（接受性能与复杂度代价） |

> 红锁不是银弹。**大多数业务用单节点 Redisson 锁就足够了**，真正需要强一致的场景，直接用 ZooKeeper/etcd 反而更可靠。红锁夹在中间，性价比要自己权衡。

---

## 2.5 三个坑的对照总结

| 坑 | 本质 | 解法 |
| :-- | :-- | :-- |
| 锁超时并发 | leaseTime 太短 | 看门狗续期 / 评估最坏耗时 |
| 误删锁 | 释放时没校验归属 | `isHeldByCurrentThread()` + Lua 原子 |
| 主从丢锁 | 异步复制，主宕机锁丢失 | 红锁 / ZooKeeper / etcd |

---

## 2.6 本章小结

| 要点 | 说明 |
| :-- | :-- |
| 锁超时 | 业务超 leaseTime 导致并发，用看门狗 |
| 误删锁 | 释放前校验归属，Redisson 已内置 |
| 主从丢锁 | 异步复制导致，红锁/强一致存储兜底 |
| 务实原则 | 一般业务单节点锁够用，别过度设计 |

> 分布式锁的三个坑，本质都指向一个词：**边界**。锁的边界（时间）、持有者的边界（谁加的）、一致性的边界（主从同步）。理解了边界，就不会踩坑。
